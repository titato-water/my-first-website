== SNS 사이트 DB 구조 정리 ==

※ 검토 메모: UI 기획서(기획서.txt)에 이미 있는 기능(팔로우, 좋아요, 신고/차단,
하루 꿀팁, 단체 채팅방, IT기기 추천/비추천)에 필요한 테이블이 이 문서에는
빠져 있어서 아래에 함께 채워 넣었습니다. 이미지 저장 방식은 프로토타입
단계에서 Unsplash를 사용하는 것으로 확정했습니다 ("게시물 작성 방식" 참고).
모든 테이블명은 서비스명(I'tel)에 맞춰 **it_** 접두사를 붙였습니다.

사용자 정보 (it_users 테이블)
- SNS 로그인/프로필 화면에서 필요한 정보들:
  * 사용자 번호: (자동으로 1, 2, 3... 증가)
  * 사용자명: (@ 표시되는 고유 아이디)
  * 이메일: (로그인할 때 사용)
  * 비밀번호: (로그인할 때 사용)
  * 표시 이름: (프로필에 보이는 실제 이름)
  * 소개글: (프로필에 보이는 자기소개)
  * 프로필 사진: (프로필 이미지 경로)
  * 생년월일: (만 14세 이상 가입 검증용 — 기획서.txt 회원가입 항목에는 있는데
    이 문서엔 빠져 있던 필드. 프로필 화면에는 노출하지 않음)
  * 가입일: (언제 가입했는지)

게시물 정보 (it_posts 테이블)
- SNS 피드 화면에서 필요한 정보들:
  * id: (게시물 고유번호 - 자동으로 1, 2, 3... 증가)
  * user_id: (작성자 ID - it_users 테이블과 연결)
  * caption: (사진에 쓴 글 내용)
  * created_at: (작성일 - 언제 올렸는지)
  * image_url: (게시물 대표 이미지 URL 또는 저장 경로)
  * video_url: (영상을 올렸을 경우의 영상 경로 - 기획서.txt의 "영상 추가"
    기능을 위해 추가. 이미지만 있으면 비워둠)
  * device_rating: (작성자가 매긴 본인 IT기기 별점, 1~5 - 기획서.txt
    게시물 작성 페이지 특징 "본인의 IT기기 별점"에 해당)
  * location: (위치 기반 추천 장소 텍스트/좌표 - 사용자가 직접 검색해서
    선택한 장소만 저장. 자동 GPS 수집 아님)
  * likes_count: (좋아요 수 - 아래 "좋아요 상세" 항목 참고)
  * recommend_count / not_recommend_count: (추천/비추천 수 - 아래
    "추천·비추천 상세" 항목 참고)
  * comments_count: (댓글 수 - 현재 댓글 개수를 숫자로 저장)
  * shares_count: (공유 수 - 현재 공유된 개수를 숫자로 저장)
  * is_story: (하루 꿀팁 여부 true/false — 기획서.txt "사람들의 하루
    꿀팁(24시간 뒤 사라짐)" 기능. 상세 로직은 아래 "하루 꿀팁" 항목 참고)

게시물 작성 방식: (확정 — 프로토타입 단계는 Unsplash 사용)
- 1단계 캡션 입력 → 2단계 Unsplash API로 랜덤 이미지 여러 개 노출 →
  3단계 마음에 드는 이미지 선택(새로고침으로 다른 이미지도 가능) →
  4단계 선택한 이미지 링크를 it_posts.image_url에 저장
- 실제 IT기기 사진이 아니라 랜덤 스톡 이미지이므로 "본인의 IT기기를
  공유"한다는 서비스 핵심 가치와는 완전히 맞지는 않지만, 임시(프로토타입)
  단계로 진행하기로 확정했습니다.
- video_url 필드는 Unsplash로 대체할 수 없으므로(이미지 전용 API) 당분간
  비워두고, 영상 업로드 기능은 실제 Supabase Storage 업로드 방식으로
  전환하는 시점에 함께 구현합니다.
- 추후 실제 서비스로 전환할 때는 Supabase Storage 업로드 방식(이미지 최대
  10MB, 영상 최대 100MB·60초)으로 교체 예정이며, image_url/video_url
  필드 구조는 그대로 재사용 가능합니다.

댓글 정보 (it_comments 테이블)
- 게시물 댓글을 위한 정보들:
  * 댓글 번호: (자동으로 1, 2, 3... 증가)
  * 댓글 내용: (댓글에 쓴 글)
  * 댓글 작성자: (누가 댓글을 썼는지 - it_users 테이블과 연결)
  * 댓글 달린 게시물: (어떤 게시물에 댓글을 달았는지 - it_posts 테이블과 연결)
  * 댓글 작성일: (언제 댓글을 썼는지)

좋아요 상세 (it_post_likes 테이블) — 신규 추가
- 지금처럼 it_posts.likes_count 숫자만 저장하면, 같은 사용자가 여러 번 눌러
  수를 조작하거나 좋아요를 취소할 수 없는 문제가 생깁니다. "누가" 좋아요를
  눌렀는지 기록하는 테이블이 별도로 필요합니다.
  * 좋아요 누른 사용자: (it_users 테이블과 연결)
  * 좋아요 누른 게시물: (it_posts 테이블과 연결)
  * 좋아요 누른 시각
  * (같은 사용자 + 같은 게시물 조합은 한 번만 저장되도록 제한 - 중복 좋아요 방지)

추천·비추천 상세 (it_post_reactions 테이블) — 신규 추가
- 기획서.txt 마이페이지의 "추천한 IT기기의 수와 비추천한 IT기기 수",
  게시물 작성 페이지의 "추천과 비추천 탭" 기능을 위해 필요합니다.
  좋아요와 마찬가지로 "누가 추천/비추천 했는지"를 저장해야 중복 클릭을
  막고 취소도 가능합니다.
  * 반응 누른 사용자: (it_users 테이블과 연결)
  * 반응 대상 게시물: (it_posts 테이블과 연결)
  * 반응 종류: (추천 또는 비추천 중 하나)
  * 반응 누른 시각
  * (같은 사용자 + 같은 게시물 조합은 한 번만 저장 - 추천/비추천 중 하나만 선택 가능)

팔로우 관계 (it_follows 테이블) — 신규 추가
- 마이페이지의 "나의 팔로워 수", "내가 팔로잉한 사람의 수"를 계산하려면
  누가 누구를 팔로우하는지 저장하는 테이블이 필요합니다. (기존 문서에는
  이 테이블이 전혀 없었습니다)
  * 팔로우 하는 사람: (it_users 테이블과 연결)
  * 팔로우 받는 사람: (it_users 테이블과 연결)
  * 팔로우 시작 시각

하루 꿀팁 (it_stories 테이블) — 신규 추가
- it_posts 테이블에 is_story만 표시하는 대신, 24시간 뒤 자동으로 사라지는
  콘텐츠는 성격이 달라서 별도 테이블로 관리하는 것을 권장합니다.
  * 작성자: (it_users 테이블과 연결)
  * 이미지/영상 경로
  * 작성 시각
  * 만료 시각: (작성 시각 + 24시간으로 자동 계산 — 이 시각이 지나면 목록
    조회에서 제외. 완전 삭제는 하지 않음)

신고/차단 (it_reports, it_blocks 테이블) — 신규 추가
- 기획서.txt의 게시물 상세 페이지 "신고/차단" 기능, 채팅방 제재 규정
  (욕설 시 정지, 성적 콘텐츠 즉시 영구정지)을 실제로 처리하려면 신고 내역과
  차단 관계를 저장할 테이블이 필요합니다.
- it_reports 테이블
  * 신고한 사용자: (it_users 테이블과 연결)
  * 신고 대상: (게시물/댓글/사용자 중 무엇인지 구분 + 대상 번호)
  * 신고 사유
  * 처리 상태: (접수/검토중/처리완료)
  * 신고 시각
- it_blocks 테이블
  * 차단한 사용자: (it_users 테이블과 연결)
  * 차단 당한 사용자: (it_users 테이블과 연결)
  * 차단 시각

단체 채팅방 (it_chat_rooms, it_chat_room_members, it_messages 테이블) — 신규 추가
- 기획서.txt에서 3차 개발 범위로 확정된 "추가 페이지: 단체 채팅방" 기능을
  위한 최소 구조입니다. 3차 개발 단계에서 상세 설계가 더 필요합니다.
- it_chat_rooms 테이블: 채팅방 번호, 채팅방 이름/주제, 생성 시각
- it_chat_room_members 테이블: 채팅방 번호, 참여자(it_users 테이블과 연결), 입장 시각
- it_messages 테이블: 메시지 번호, 채팅방 번호, 보낸 사람, 내용(텍스트/사진/위치
  구분), 보낸 시각

알림 (it_notifications 테이블) — 신규 추가, 선택 사항
- 모바일 UI 특징에 하단 탭 바 "알림" 항목을 넣었으므로, 좋아요·댓글·팔로우
  발생 시 알림을 보여주려면 아래 테이블이 필요합니다. (기획서.txt에 명시된
  필수 기능은 아니라서 2차 개발 이후 여유 있을 때 추가해도 됩니다)
  * 알림 받는 사람: (it_users 테이블과 연결)
  * 알림 발생시킨 사람: (it_users 테이블과 연결)
  * 알림 종류: (좋아요/댓글/팔로우/추천 등)
  * 알림 대상: (게시물 또는 댓글 번호)
  * 읽음 여부
  * 알림 발생 시각

SNS 테이블 연결 관계 (정리)
- 사용자 게시물: 한 사용자가 여러 게시물 작성 가능 (it_users 1 : N it_posts)
- 사용자 댓글: 한 사용자가 여러 게시물에 댓글 가능 (it_users 1 : N it_comments)
- 게시물 댓글: 한 게시물에 여러 사용자가 댓글 가능 (it_posts 1 : N it_comments)
- 게시물 좋아요: 사용자와 게시물 사이의 N:M 관계 (it_post_likes 경유)
- 게시물 추천/비추천: 사용자와 게시물 사이의 N:M 관계 (it_post_reactions 경유)
- 팔로우: 사용자와 사용자 사이의 N:M 관계, 자기 자신을 참조 (it_follows 경유)
- 신고: 사용자가 게시물/댓글/다른 사용자를 신고 (it_reports 경유)
- 차단: 사용자와 사용자 사이의 N:M 관계 (it_blocks 경유)
- 채팅: 사용자와 채팅방 사이의 N:M 관계 (it_chat_room_members 경유), 채팅방에
  여러 메시지 (it_chat_rooms 1 : N it_messages)
- 알림: 한 사용자가 여러 알림을 받음 (it_users 1 : N it_notifications)
